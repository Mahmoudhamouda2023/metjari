# غزة ديلفري — المرحلة الأولى: الحسابات والصلاحيات والمتاجر

الإصدار: 0.1.1 — Laravel 12 — 24 أكتوبر 2026.

هذه حزمة مصدر Laravel مستقلة لتنفيذ أساس الحسابات والمتاجر. يمكن دمجها بالمشروع عبر Composer كمكتبة محلية؛ ليست تطبيق ويب مكتملًا ولا تحتوي على صفحات دخول أو واجهات أو تشغيل طلبات فعلية. لم يُرفق مشروع Laravel قائم، لذلك لم تُعدّل ملفات مشروع سابق.

## ما تم تنفيذه

- فصل حسابات الإدارة والكباتن في `staff` عن أصحاب المتاجر في `users`.
- فصل بيانات المتجر في `stores` وبيانات وسيلة التوصيل في `captain_profiles`.
- صلاحيات وأدوار عبر `spatie/laravel-permission`، مع فصل التشغيل عن الاعتماد المالي.
- Migrations وفهارس وقيود ملكية وعلاقات، وModels تخفي كلمات المرور وتشفّرها بالـ hashing.
- إنشاء التاجر ومتجره بحالة انتظار ضمن معاملة واحدة؛ المستخدم لا يختار الدور أو حالة التفعيل.
- خدمة مراجعة المتجر وتغيير حالته مع تحديث حالة مالكه وتسجيل القرار.
- استعلامات وقواعد وصول تعزل بيانات كل تاجر، وتمنع الكابتن من تصفّح كل المتاجر.
- إنشاء حسابات الفريق بواسطة المشرف العام، وحماية آخر مشرف فعّال من الإيقاف.
- أساس لإبطال الجلسات على الطلب المحمي التالي بعد إيقاف الحساب.
- أمر لإنشاء أول مشرف عام دون كلمة مرور افتراضية أو إظهار كلمة المرور في الطرفية.
- اختبارات تكامل للملكية والصلاحيات والتسجيل والجلسات والمعاملات.

التفاصيل: [مخطط قاعدة البيانات](docs/DATABASE_SCHEMA_AR.md)، [الصلاحيات](docs/ACCESS_CONTROL_AR.md)، [التوافق](docs/COMPATIBILITY_AR.md)، [التحقق](docs/VALIDATION_AR.md).

## حدود هذه المرحلة

الواجهات، Controllers، تسجيل الدخول الفعلي، استعادة كلمة المرور، تأكيد ملكية الجوال، تغيير كلمة المرور المؤقتة، عناوين الاستلام ومناطق الخدمة، التسعير، الكوبونات والباقات والطلبات والحسابات المالية ستُنفّذ في مراحلها. أسماء بعض الصلاحيات المستقبلية موجودة لتثبيت العقد بين الأجزاء، ولا تعني أن وظائفها نُفّذت.

حالة المتجر `active` تعني اعتماد حسابه إداريًا فقط. عند بناء الطلبات، يجب التحقق أيضًا من وجود اتفاق تسعير صالح ومنطقة خدمة فعّالة قبل قبول أول طلب؛ هذه الحزمة لا تحتوي على نقطة استقبال طلبات.

المتجر مرتبط بمالك واحد، ولكل حساب تاجر متجر واحد في هذا الإصدار. حساب الموظف يمكنه حمل أكثر من دور عند الحاجة، دون إنشاء بيانات دخول مكررة. لا توجد أسعار أو رسوم باقات أو بيانات هوية فعلية أو كلمات مرور جاهزة داخل المصدر.

## تثبيت الحزمة في مشروع جديد

1. ضع مجلد الحزمة في `packages/gaza-delivery-foundation` داخل مشروع Laravel.
2. استخدم Laravel 12 وPHP 8.2 أو أحدث ضمن الإصدارات التي يدعمها الإطار. حزمة الحسابات لا تثبّت مكتبة الجداول بعد؛ الإصدار المناسب لجداول الواجهة هو Yajra 12، بدل Yajra 10 غير المتوافق مع اختيار Laravel 12.
3. في مشروع جديد **لم تُشغّل عليه migrations بعد**، أزل من خطة الترحيل إنشاء `users` الافتراضي؛ هذه الحزمة تنشئ الجدول المطلوب ببدائل واضحة. إذا كان الجدول موجودًا أو عليه بيانات، يلزم إعداد ترحيل تكميلي خاص بذلك المشروع، ولا يُحذف الجدول أو تُستبدل بياناته. الحزمة تتوقف صراحة عند وجود جدول بنفس الاسم.
4. أضف مستودع Composer محليًا، ثم ثبّت الحزمة:

```bash
composer config repositories.delivery-foundation path packages/gaza-delivery-foundation
composer require gaza-delivery/foundation:@dev
```

5. انشر migration مكتبة الصلاحيات مرة واحدة فقط. إذا كان المشروع يستخدم Spatie مسبقًا، راجع مخططه الحالي بدل نشر نسخة مكررة:

```bash
php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider" --tag="permission-migrations"
php artisan migrate
php artisan db:seed --class="GazaDelivery\Foundation\Database\Seeders\AccessControlSeeder"
php artisan delivery:bootstrap-admin
```

الـ Seeder يعيد الأدوار النظامية إلى مصفوفة الصلاحيات الموثقة؛ شغّله أثناء الإعداد أو ضمن تغيير مدروس، وليس مع كل طلب HTTP. إذا خصّصت صلاحيات الأدوار لاحقًا، راجع أثر إعادة تشغيله.

لا تضع كلمات مرور أو بيانات حقيقية في Seeder. أمر المشرف العام يطلب كلمة المرور بشكل مخفي، ويرفض إنشاء مشرف أول إضافي بعد وجود أحدهم.

## عقد الدمج لمرحلة تسجيل الدخول

المزوّد يسجل حارسين منفصلين: `staff` و`merchant`، دون تغيير حارس المشروع الافتراضي. يجب أن تختار صفحات الدخول الحارس من مسار السيرفر؛ لا تُجرَّب كلمة المرور في الجدولين تلقائيًا، ولا يُقبل الدور من حقل متصفح لتحديد صلاحية الحساب.

بعد نجاح التحقق من كلمة المرور، تجدَّد الجلسة ويُحفظ إصدارها:

```php
$request->session()->regenerate();
$request->session()->put('delivery_auth.staff.version', $staff->session_version);
```

للتاجر يستخدم المفتاح `delivery_auth.merchant.version`. هذه أسطر عقد دمج، وليست بديلًا عن Controller دخول كامل. لا تفتح مسار دخول عام لها مباشرة.

المسارات المحمية للموظف تستخدم `web` ثم `auth:staff` ثم `delivery.active:staff`. ومسارات التاجر تستخدم نظائرها مع `merchant`. طبّق السياسات فوق ذلك لكل مورد. Middleware الحالة لا يمنح صلاحية إدارة أو صلاحية مالية بمفرده.

الجلسة القديمة لا تُحذف من مخزن الجلسات في الحال؛ تصبح غير صالحة على الطلب المحمي التالي. تسجيل الدخول بالـ remember-me غير منفّذ حاليًا؛ لا تفعّله قبل تصميم تكامله مع إصدار الجلسة. صفحات انتظار المراجعة تتطلب مسارات منفصلة للعرض المحدود، ولا توضع خلف middleware الذي يشترط `active`.

## الاستخدام داخل طبقة التطبيق

استدعِ الخدمات `MerchantRegistration` و`StaffAccounts` و`StoreReview` من Controllers قصيرة بعد تطبيق CSRF وrate limiting والتحقق من الهوية. استخدم `StoreDirectory` في القوائم والبحث والتصدير، ولا تبدأ استعلامات التاجر من `Store::query()` غير مقيّدة بالملكية.

كل البيانات الحساسة محمية من التعبئة الجماعية؛ الخدمات تختار الحقول صراحة. لا تستخدم `forceFill($request->all())`، ولا تقبل هوية الموظف المنفذ من المتصفح.

سجل التدقيق يرفض التعديل والحذف عبر Model. يجب أيضًا قصر صلاحيات قاعدة بيانات الإنتاج على التطبيق ومنع الاستخدام المباشر لحذف السجل؛ حماية Model لا تمنع مدير قاعدة البيانات أو استعلام SQL مباشرًا.

## تشغيل اختبارات الحزمة

من داخل مجلد الحزمة:

```bash
composer install
composer test
composer lint
```

الاختبارات تستخدم SQLite في الذاكرة وبيانات اصطناعية فقط. نتائج التحقق الفعلية وحدوده موثقة في `docs/VALIDATION_AR.md`. قبل تشغيل حقيقي يلزم فحص الترحيلات والمعاملات على قاعدة الإنتاج المختارة، واختبارات الدخول والواجهات عندما تُنفّذ.
